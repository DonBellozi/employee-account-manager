# Employee Offboarding Manager

Внутренняя веб-система **«Управление жизненным циклом учетных записей»** для сопровождения работников от создания учетных записей до окончательного увольнения.

Техническое имя проекта: `employee-offboarding-manager`.

## Основной контур

Система объединяет:

- кадровые XLSX-выгрузки 1С ЗУП из нескольких организаций;
- единый идентификатор человека через HMAC от СНИЛС без хранения исходного СНИЛС;
- сверку и управление Active Directory;
- сверку и управление Zimbra;
- уведомления сотрудникам об увольнении и возврате оборудования;
- read-only проверку оборудования в IT Invent;
- автоматическую финальную блокировку после контрольной кадровой выгрузки;
- журнал действий и Telegram-уведомления;
- ручное создание и блокировку учетных записей.

Проект работает в режиме опытной эксплуатации. Глобальный `DRY_RUN` снят: штатные разрешенные действия выполняются реально. Отдельные функции предпросмотра и планирования остаются безопасными и не заменяют боевой режим приложения.

## Кадровые данные

Приложение круглосуточно проверяет IMAP на наличие новых полных XLSX-выгрузок. Для destructive-действий используется контрольная выгрузка после 19:00 по всем включенным кадровым источникам.

Отсутствие работника в актуальной полной выгрузке одной организации означает прекращение работы именно в этой организации. Перед окончательной блокировкой учитываются все подключенные организации.

## Увольнение

После подтвержденного окончательного увольнения система может:

1. отправить уведомление о возврате оборудования;
2. проверить наличие выданного оборудования в IT Invent;
3. отключить учетную запись AD;
4. закрыть соответствующие физические ящики Zimbra;
5. сразу выполнить точечную повторную сверку AD/Zimbra;
6. сохранить результат и возможные ошибки в журнале.

Автоматическая финальная блокировка выполняется не ранее 19:10 и только после готовности контрольных кадровых выгрузок.

## Запуск

Для существующей установки:

```bash
sudo docker compose up -d --build --remove-orphans
curl -i http://127.0.0.1:8081/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Docker service и container после переименования:

```text
employee-offboarding-manager
```

Пример выполнения служебной команды внутри контейнера:

```bash
docker compose exec employee-offboarding-manager python scripts/create_local_user.py operator1 --role operator
```

## Конфигурация

Для новой установки используются:

```dotenv
APP_NAME=Управление жизненным циклом учетных записей
SESSION_COOKIE_NAME=employee_offboarding_manager_session
```

Перед рабочим запуском `APP_SECRET_KEY` должен быть заменен на собственное длинное случайное значение. Приложение не запускается с ключом вида `change-me...`.

## Active Directory

AD используется как общая учетная запись человека в инфраструктуре. При межорганизационном сопоставлении приоритет имеет сохраненный `objectGUID`.

## Zimbra

Zimbra проверяется по стабильному `zimbraId` и адресам/алиасам. В реестре отображается фактический `zimbraAccountStatus`, включая `active`, `closed`, `locked`, `lockout`, `maintenance` и `pending`.

Почтовые учетные записи являются организационно-зависимыми: адрес одной организации не переносится автоматически в другую только по совпадению человека.

## Сопоставление объекта с работником

Кадровая выгрузка — единственный источник правды о людях. Каждая интеграция
при этом видит свой мир: Zimbra — адреса, Synology — логины и описания, AD —
учетные записи. Связывает одно с другим единый резолвер
`app/services/worker_identity.py`, и им обязаны пользоваться все контуры.

Признаки проверяются по убыванию надежности:

1. **адреса** — `corporate_email`, `personal_email`, а также `source_email` и
   `zimbra_email` из ручного сопоставления;
2. **логины** — `login` из выгрузки, `ad_login` из сопоставления и локальная
   часть адреса;
3. **ФИО** — с нормализацией регистра, лишних пробелов и `ё`/`е`.

Работник считается действующим, если он присутствует в актуальной выгрузке
или его занятость хотя бы в одной организации имеет статус `active`/`scheduled`.

Ключевой принцип: **отсутствие совпадения означает нехватку данных, а не
отсутствие человека**, и трактуется в пользу работника. Ни один контур не
имеет права выполнить блокирующее действие на одном лишь основании «не нашли».

Причина такой строгости историческая. Раньше каждый контур сопоставлял
по-своему, и оба — Synology и наблюдение Zimbra — опирались на точное
совпадение единственного поля `corporate_email`. Работник с алиасом,
незаполненным или отличающимся адресом защиты не получал: в одном случае его
учетную запись отключали как «уволенную», в другом закрывали почтовый ящик по
неактивности.

## Единый контур увольнения

Решение о том, что человек уволен окончательно, принимается **один раз** по
кадровым данным: `UpcomingDismissalService` собирает кандидата по `worker_key`
с учетом всех организаций, всех должностей и ручных отсрочек. Отдельные
интеграции этот вывод не переоткрывают.

`FinalDismissalLifecycleService` блокирует все учетные записи человека одним
прогоном. Каждая система — цель (`FinalDismissalBlockTarget.system`) внутри
общего прогона:

| Система | Действие |
| --- | --- |
| `ad` | отключение учетной записи AD |
| `zimbra` | закрытие физических ящиков |
| `synology` | `Expired=1` на локальной учетке DSM |

Отсюда следуют общие для всех систем свойства: одно окно, одни ретраи, один
interlock `_still_due` перед каждым внешним изменением, одна запись прогона на
человека и общая отмена, если кадровая ситуация изменилась.

Цель Synology создается только для учетной записи с заполненным `worker_key`,
то есть однозначно сопоставленной с этим человеком. Несопоставленные записи в
блокировку по увольнению не попадают никогда.

## Единое окно плановых блокировок

Плановые блокировки выполняются не ранее **19:10**. При неудаче попытка
повторяется каждые **10 минут**, но не более **6 раз за сутки**; остаток
переносится на следующий вечер. Константы находятся в
`app/services/blocking_window.py` и не дублируются по модулям.

Ручная блокировка из раздела «Блокировка» в это окно не входит: оператор
запускает ее осознанно и ждать вечера не должен.

Кадровый контроль (полные выгрузки текущего дня после 19:00 по всем источникам)
требуется только там, где решение действительно зависит от кадровых данных.
Внешние и нераспознанные учетные записи Synology блокируются независимо от
состояния выгрузок.

## Synology DSM

Контур существует, чтобы увести работников с локальных учетных записей на
доменную авторизацию.

### Порядок фильтрации

Порядок принципиален и идет от безопасного к решительному:

1. **системная запись DSM** (`admin`, `root`, `guest`, UID меньше 1024) —
   не трогаем никогда;
2. **человек есть в кадровой выгрузке и работает** — не трогаем как
   уволенного; он попадает в обычный 3-месячный миграционный цикл;
3. **список исключений** — не трогаем;
4. только после этого учитываются домен, увольнение и внешние доступы.

Человек ищется общим для проекта правилом — см. раздел «Сопоставление объекта
с работником».

### Что блокирует сам контур Synology

Увольнением он **не занимается**: это задача общего контура, который отключает
AD, Zimbra и DSM одним прогоном. Здесь остается только собственная задача —
увод работников с локальных учетных записей на доменную авторизацию:

- внешние учетные записи после истечения 6-месячного цикла контроля;
- действующие работники после истечения 3-месячного цикла, который выдается
  постепенными случайными пакетами.

Классификация `internal_dismissed` по-прежнему вычисляется и видна в
интерфейсе, но действие по ней не выполняется: блокировку выполнит общий
контур по кадровому решению.

### Что не блокируется автоматически

Учетная запись, которую **не удалось сопоставить** ни с одним человеком,
получает статус «требует классификации» и не отключается. Отсутствие
сопоставления означает нехватку данных, а не отсутствие работника, и
трактуется в его пользу. Такие записи разбираются вручную: служебные
заносятся в исключения, остальные — в кадровое сопоставление.

Ошибочно заблокированную запись можно включить обратно на странице интеграции
(`Expired=0`). Автоматика включением не занимается никогда: это всегда явное
действие администратора, и оно фиксируется в журнале. После восстановления
автоматические действия по записи приостанавливаются до ручного решения.

Write-scope интеграции ограничен одним действием: отключение локальной учетной
записи через `Expired=1`. Удаление и автоматическое включение не выполняются.

Этап блокировок защищен предохранителем. Если за один прогон к отключению
готово больше учетных записей, чем задано в политике (`Максимум блокировок за
прогон`, по умолчанию 10), блокировки не выполняются вообще: такой объем чаще
означает неполную кадровую выгрузку, а не массовое увольнение. Прогон
завершается со статусом `partial`, в журнал пишется
`synology_mass_disable_blocked`, а на странице `/settings/synology` появляется
требование ручного подтверждения.

Подтверждение одноразовое, действует 60 минут и только на тот объем, который
видел администратор. Изменение лимита в политике сбрасывает ранее выданное
подтверждение.

Каждое примененное к DSM изменение фиксируется в БД отдельной транзакцией:
ошибка на следующей учетной записи не откатывает журнал уже выполненных
блокировок.

## IT Invent

Интеграция с IT Invent выполняет только `SELECT`. Приложению следует выдавать отдельную SQL-учетную запись только с правами чтения.

Наличие оборудования формирует предупреждение и используется в процессе возврата имущества, но само по себе не должно технически блокировать действие над AD/Zimbra.

## Совместимость после переименования

Имя существующего Docker volume `account-provisioner-data` намеренно не меняется этим патчем. В нем находится рабочая SQLite-база и другие постоянные данные. Переименование тома без отдельной миграции могло бы привести к запуску приложения с пустой базой.

По той же причине Compose project-id временно закреплен как `account-provisioner`. Это внутренний compatibility-идентификатор: сервис и контейнер уже называются `employee-offboarding-manager`, а каталог проекта можно безопасно переименовать без появления нового пустого тома.

По той же причине внутренние имена существующих таблиц БД не переименовываются: это технические идентификаторы хранения, а не название проекта.

CA-сертификаты и `known_hosts` намеренно продолжают подключаться из `/opt/account-provisioner/...`. Это compatibility-путь для уже существующих рабочих файлов и не зависит от имени стека Portainer.
