# Employee Offboarding Manager

Внутренняя веб-система **«Управление жизненным циклом учетных записей»** для сопровождения работников от создания учетных записей до окончательного увольнения.

Техническое имя проекта: `employee-offboarding-manager`.

## Основной контур

Система объединяет:

- кадровые XLSX-выгрузки 1С ЗУП из нескольких организаций;
- единый идентификатор человека через HMAC от СНИЛС без хранения исходного СНИЛС;
- сверку и управление Active Directory;
- сверку и управление Zimbra;
- уведомления сотрудникам об увольнении и возврате оборудования;
- read-only проверку оборудования в IT Invent;
- автоматическую финальную блокировку после контрольной кадровой выгрузки;
- журнал действий и Telegram-уведомления;
- ручное создание и блокировку учетных записей.

Проект работает в режиме опытной эксплуатации. Глобальный `DRY_RUN` снят: штатные разрешенные действия выполняются реально. Отдельные функции предпросмотра и планирования остаются безопасными и не заменяют боевой режим приложения.

## Кадровые данные

Приложение круглосуточно проверяет IMAP на наличие новых полных XLSX-выгрузок. Для destructive-действий используется контрольная выгрузка после 19:00 по всем включенным кадровым источникам.

Отсутствие работника в актуальной полной выгрузке одной организации означает прекращение работы именно в этой организации. Перед окончательной блокировкой учитываются все подключенные организации.

## Увольнение

После подтвержденного окончательного увольнения система может:

1. отправить уведомление о возврате оборудования;
2. проверить наличие выданного оборудования в IT Invent;
3. отключить учетную запись AD;
4. закрыть соответствующие физические ящики Zimbra;
5. сразу выполнить точечную повторную сверку AD/Zimbra;
6. сохранить результат и возможные ошибки в журнале.

Автоматическая финальная блокировка выполняется не ранее 19:10 и только после готовности контрольных кадровых выгрузок.

## Запуск

Для существующей установки:

```bash
sudo docker compose up -d --build --remove-orphans
curl -i http://127.0.0.1:8081/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Docker service и container после переименования:

```text
employee-offboarding-manager
```

Пример выполнения служебной команды внутри контейнера:

```bash
docker compose exec employee-offboarding-manager python scripts/create_local_user.py operator1 --role operator
```

## Конфигурация

Для новой установки используются:

```dotenv
APP_NAME=Управление жизненным циклом учетных записей
SESSION_COOKIE_NAME=employee_offboarding_manager_session
```

Перед рабочим запуском `APP_SECRET_KEY` должен быть заменен на собственное длинное случайное значение. Приложение не запускается с ключом вида `change-me...`.

## Active Directory

AD используется как общая учетная запись человека в инфраструктуре. При межорганизационном сопоставлении приоритет имеет сохраненный `objectGUID`.

## Zimbra

Zimbra проверяется по стабильному `zimbraId` и адресам/алиасам. В реестре отображается фактический `zimbraAccountStatus`, включая `active`, `closed`, `locked`, `lockout`, `maintenance` и `pending`.

Почтовые учетные записи являются организационно-зависимыми: адрес одной организации не переносится автоматически в другую только по совпадению человека.

## IT Invent

Интеграция с IT Invent выполняет только `SELECT`. Приложению следует выдавать отдельную SQL-учетную запись только с правами чтения.

Наличие оборудования формирует предупреждение и используется в процессе возврата имущества, но само по себе не должно технически блокировать действие над AD/Zimbra.

## Совместимость после переименования

Имя существующего Docker volume `account-provisioner-data` намеренно не меняется этим патчем. В нем находится рабочая SQLite-база и другие постоянные данные. Переименование тома без отдельной миграции могло бы привести к запуску приложения с пустой базой.

По той же причине Compose project-id временно закреплен как `account-provisioner`. Это внутренний compatibility-идентификатор: сервис и контейнер уже называются `employee-offboarding-manager`, а каталог проекта можно безопасно переименовать без появления нового пустого тома.

По той же причине внутренние имена существующих таблиц БД не переименовываются: это технические идентификаторы хранения, а не название проекта.

CA-сертификаты и `known_hosts` намеренно продолжают подключаться из `/opt/account-provisioner/...`. Это compatibility-путь для уже существующих рабочих файлов и не зависит от имени стека Portainer.
